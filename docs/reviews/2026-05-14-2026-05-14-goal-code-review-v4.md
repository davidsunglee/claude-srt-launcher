### Outcome

**Verdict:** Not approved

**Reasoning:** The implementation is broadly complete and the unit suite passes, but the launcher does not actually enforce the required gate for `--dangerously-skip-permissions`: users can pass it through as a Claude argument on any profile. That is a core safety requirement for this tool and should be fixed before release.

### Strengths

- Policy composition is clean and deterministic, with array union/deduplication and scalar right-wins behavior implemented in a small pure function (`src/policy/compose.ts:15-58`).
- Policy validation covers important invariants beyond the minimum, including local binding/socket override checks, host `~/.ssh`/`~/.claude` deny-list preservation, deny/allow write overlap detection, and inspect-workspace nesting protection (`src/policy/validate.ts:21-85`).
- Isolated Claude state creation tightens permissions on both the state root and `.claude` subdirectory, preserving the intended `0700` invariant even on re-runs (`src/state/claude-home.ts:18-26`).
- The smoke test documents and exercises a meaningful allow/deny matrix, including denied host writes with host-side artifact checks and socket-related negative cases (`scripts/smoke-test.sh:1-21`, `scripts/smoke-test.sh:135-181`).
- The test suite is comprehensive for a first implementation; I ran `npm test` and all 107 tests passed.

### Issues

#### Critical (Must Fix)

_None._

#### Important (Should Fix)

- **`src/runner/claude-args.ts:12`: `--dangerously-skip-permissions` is not actually gated**
  - **What:** `buildClaudeArgs` correctly auto-adds `--dangerously-skip-permissions` only for `profile === 'build' && unattended`, but otherwise returns `['claude', ...userArgs]` without rejecting a user-supplied `--dangerously-skip-permissions`. Because `runCommand` passes `parsed.userArgs` directly into this function (`src/commands/run.ts:51-55`), `claude-srt run --profile interactive -- --dangerously-skip-permissions` will launch Claude with the dangerous flag outside the build/disposable/unattended gate.
  - **Why it matters:** The plan requires the dangerous Claude permissions bypass to be available only for build profile runs after the disposable-workspace gate and `--unattended` opt-in. Allowing it via pass-through arguments undermines that safety control for interactive/ios/inspect and for build runs that did not request `--unattended`.
  - **Recommendation:** Reject `--dangerously-skip-permissions` in `userArgs` unless `profile === 'build' && unattended === true` (with the existing disposable check already completed in `runCommand`). Add regression tests for interactive rejection, build-without-unattended rejection, and build-with-unattended acceptance. Update the README matrix to say the flag is unavailable for non-build profiles rather than "Allowed"/"Not recommended" (`README.md:35-38`).

#### Minor (Nice to Have)

- **`src/state/claude-home.ts:50`: Host Claude state gate reports as an unexpected error in `run`**
  - **What:** `assertNotHostClaudeHome` throws a plain `Error`, while the CLI top-level handler maps only `PolicyValidationError` and `WorkspaceNotDisposableError` to the expected user-error exit path.
  - **Why it matters:** A user configuration error such as `run --state-dir ~/.claude` exits through the generic error path rather than the same explicit policy/workspace gate used elsewhere. The message is clear, but the error classification is inconsistent.
  - **Recommendation:** Introduce a small typed error (for example `ClaudeStateError`) and handle it with exit code 2 alongside the other user-actionable gate failures.

### Recommendations

- Add an end-to-end or command-level test that constructs `run --profile interactive -- --dangerously-skip-permissions` and asserts the launcher rejects it before spawning `srt`.
- Consider documenting in the CLI help which flags are wrapper flags versus pass-through Claude flags, especially after filtering dangerous pass-through options.
