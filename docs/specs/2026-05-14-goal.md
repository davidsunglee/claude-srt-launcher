# Claude SRT Launcher and Policy Profiles

Source: TODO-13cb64bd

## Goal

Build a standalone `claude-srt-launcher` tool for running Claude Code under Anthropic Sandbox Runtime (SRT), with reusable policy profiles for interactive coding, unattended code modification, read-mostly inspection, and iOS Simulator development. The first release is a private/local tool, not a published package, and should make practical day-to-day Claude Code usage safer without claiming VM-grade isolation.

## Context

This repository is currently minimal: `README.md` contains only a short project title, and the task is captured in `docs/todos/13cb64bd.md`. There is no scout brief and no existing launcher implementation.

SRT wraps an entire process tree using native OS sandboxing primitives (`sandbox-exec` on macOS, `bubblewrap` on Linux) plus proxy-based network filtering. Its relevant policy mechanics are:

- filesystem reads are deny-then-allow, so broad host paths can be denied and the workspace can be re-allowed;
- filesystem writes are allow-only, with explicit allowed write paths;
- network egress is allow-only through configured domains;
- Unix sockets are blocked by default unless explicitly allowed;
- `allowLocalBinding` should remain false by default because current macOS behavior can weaken outbound restrictions;
- allowing Docker/OrbStack sockets is effectively host access and must not be a default.

The launcher is intentionally independent of Gondolin, Pi, and pi-interactive-subagent integration. It should still account for the kinds of Claude/Pi subagent workloads used in `/Users/david/Code/pi-config/agent/agents`: non-coordinator agents such as `spec-designer`, `planner`, `plan-reviewer`, `coder`, `code-reviewer`, `test-runner`, `verifier`, and `scout` can be mapped onto the profiles below. Coordinator/refiner agents such as `plan-refiner` and `code-refiner` remain Pi-only and are out of scope for SRT profile design.

## Requirements

- Provide a local launcher command for Claude Code under SRT, exposed through a TypeScript/Node CLI and convenient local `just` recipes.
- Keep the first release private/local. The repository may include npm-style package/bin metadata for local installability, but publishing to npm, Homebrew, or another public channel is out of scope.
- Provide four named policy profiles:
  - `interactive` — human-driven Claude Code development, permission prompts retained, practical coding egress enabled by default.
  - `build` — unattended write-capable work in a disposable workspace, suitable for Claude Code `--dangerously-skip-permissions` only behind explicit workspace guardrails.
  - `inspect` — read-mostly verification/review/test execution, with source/workspace writes blocked by default and writes limited to temp/cache/test-output/report artifacts.
  - `ios` — usable iOS Simulator build/test workflow profile, aligned with the existing safehouse alias naming.
- `interactive` must allow GitHub and common package-manager domains by default, alongside the domains required for Claude Code service operation. The exact domain list must be explicit in the generated SRT policy and documented as exfiltration-capable.
- `build` must default to Claude-service-only network access. GitHub and package-manager egress for unattended work must require an explicit named override or profile variant.
- `build` must refuse to launch unless the workspace is explicitly marked or passed as disposable, unless the user provides a clearly named unsafe override.
- `inspect` must block source/workspace writes by default, while allowing narrowly scoped temp/cache/test-output/report locations needed by tests and review artifacts.
- `ios` must support iOS Simulator build/test workflows by default, including the Xcode, Simulator, DerivedData, and cache access needed for simulator-oriented development. Physical-device signing, archive/export, and broad keychain/codesigning access are out of scope except for documented manual unsafe opt-ins.
- Normal launcher runs must use an isolated Claude Code config/auth state directory rather than the host `~/.claude` by default.
- Include a bootstrap/maintenance mode for the isolated Claude state so plugins, MCP servers, commands, agents, and related packages can be installed or updated without using the host `~/.claude`.
- Direct use of the host `~/.claude` must be an explicit unsafe override, not a default or silent fallback.
- Keep `allowLocalBinding: false` in default profiles, avoid carrying a local SRT patch in the first release, and document that local binding currently requires an unsafe opt-in.
- Keep `allowAllUnixSockets` false by default. Any specific Unix socket allowance must be profile-specific, documented, and absent from the default `interactive`, `build`, and `inspect` profiles.
- Do not allow Docker, OrbStack, SSH agent, cloud credential, password manager, or unrelated home-directory sockets by default. Documentation must explain that allowing Docker/OrbStack sockets is effectively host access.
- Provide an executable smoke-test script that verifies the core allow/deny behavior, with README commands documenting what it checks.
- Provide README documentation explaining when to use each profile, what each profile protects, remaining holes, unsafe overrides, and when to escalate to VM isolation.

## Constraints

- SRT is a baseline sandbox boundary, not a replacement for Tart/Gondolin/VM isolation for hostile-code scenarios.
- Defaults must prefer explicit allowlists over broad host access, especially for writes, Unix sockets, and sensitive host credentials.
- Broad network domains such as GitHub and package registries must be treated as possible exfiltration channels even when they are useful for developer workflows.
- The launcher must not expose host `~/.ssh`, cloud credentials, password manager sockets, Docker/OrbStack sockets, or unrelated home directories by default.
- The implementation must not depend on Pi, Gondolin, pi-interactive-subagent, or their runtime APIs.
- Profile names are fixed for this release: `interactive`, `build`, `inspect`, and `ios`.
- The first release should be practical on macOS, especially for Claude Code and iOS Simulator workflows; Linux support may follow SRT capabilities but must not weaken macOS defaults.

## Approach

**Chosen approach:** Use a TypeScript/Node CLI and policy generator as the safety/enforcement layer, plus a `justfile` as the ergonomic local command surface. The CLI owns profile composition, validation, isolated Claude state selection, disposable-workspace checks, unsafe override handling, and invocation of `srt`; `just` recipes expose common workflows such as `interactive`, `build`, `inspect`, `ios`, bootstrap/maintenance, and smoke tests.

**Why this over alternatives:** The policy set has reusable defaults, profile-specific overrides, explicit unsafe paths, and guardrails that benefit from code-level validation rather than ad hoc shell templating. A `justfile` keeps the local developer interface convenient without making shell recipes the trust boundary.

**Considered and rejected:**

- Static JSON profiles plus a thin shell/Node launcher — transparent and simple, but profile variants, unsafe overrides, isolated state, and disposable-workspace checks would become repetitive or under-validated.
- Pure shell scripts with embedded JSON templates — minimal dependencies, but harder to validate, test, and maintain as policy complexity grows.
- Public package-first design — premature for a security-sensitive local tool whose defaults and SRT behavior need validation before distribution.

## Acceptance Criteria

- Running the launcher with `interactive` starts Claude Code under SRT with permission prompts retained, isolated Claude state selected by default, workspace access allowed, and GitHub/common package-manager egress documented and enabled.
- Running the launcher with `build` refuses to proceed without an explicit disposable workspace marker/argument unless a clearly named unsafe override is supplied.
- Running the launcher with `build` supports Claude Code `--dangerously-skip-permissions` only inside the SRT profile and disposable-workspace guardrails.
- Running the launcher with `inspect` permits read/test/review workflows while blocking direct source/workspace writes outside the allowed temp/cache/test-output/report paths.
- Running the launcher with `ios` can support an iOS Simulator build/test workflow without requiring broad host credential exposure by default.
- The smoke-test script proves that allowed workspace reads/writes work where intended, denied host secrets cannot be read, denied host paths cannot be written, non-allowlisted network egress is blocked, and Claude Code can start through the wrapper.
- The smoke-test script includes negative checks for sensitive paths or sockets such as SSH credentials, cloud credentials, Docker/OrbStack sockets, and unrelated home-directory access where feasible on the host platform.
- Bootstrap/maintenance mode can update the isolated Claude Code state without silently using host `~/.claude`.
- Documentation clearly lists each profile, intended use, default network stance, filesystem read/write stance, unsafe overrides, known holes, and when VM isolation is required.
- Documentation explicitly warns that GitHub/package-manager domains, Docker/OrbStack sockets, host Claude state, local binding, and broad Xcode/iOS exceptions can weaken isolation or enable exfiltration.
- The implementation remains independent of Gondolin, Pi, and pi-interactive-subagent integrations.

## Non-Goals

- No Gondolin integration.
- No Pi integration.
- No pi-interactive-subagent integration.
- No public package publishing in the first release.
- No local SRT patch for `allowLocalBinding` behavior in the first release.
- No claim that SRT provides VM-grade isolation for hostile code.
- No default support for physical iOS device signing, archive/export, or broad keychain/codesigning access.
- No default access to Docker, OrbStack, SSH agent, cloud credential, password manager, or host Claude config sockets.
