# Migrate project package manager from npm to pnpm

Source: TODO-61ad31eb

## Goal

Replace npm with pnpm as the canonical package manager for the launcher repo. The change covers the committed lockfile, the `packageManager` field in `package.json`, pnpm's required build-script approval for `esbuild`, every npm/npx invocation across `package.json` scripts, the `justfile`, and the README, plus a sandbox-policy extension that grants pnpm's macOS default store/cache paths the same filesystem allowances currently granted to `~/.npm` in the relevant profiles. The migration also cleans up `ios` profile composition so package-manager cache/store and registry allowances added to `interactive` do not leak into `ios`; the rendered iOS policy remains an explicit allowlist for iOS workflows. After the migration, the project's own dev workflow runs entirely on pnpm and continues to function inside the launcher's own sandbox profiles.

## Context

The launcher repo currently uses npm: `package-lock.json` is committed; `package.json` scripts invoke `npm run build`; the `justfile` invokes `npm install` and `npx tsc` / `npx vitest`; the README install and smoke sections reference `npm install` / `npm run build` / `npm run smoke`. There are 13 test files / 114 tests passing under the current setup.

A scratch migration confirmed pnpm 11 works against this codebase. `pnpm import` generated `pnpm-lock.yaml`. `pnpm install` initially failed with `ERR_PNPM_IGNORED_BUILDS` for `esbuild@0.21.5` because pnpm 11 no longer auto-runs install/build scripts of transitive dependencies. `pnpm approve-builds --all` produced a `pnpm-workspace.yaml` containing:

```yaml
allowBuilds:
  esbuild: true
```

After that approval, `pnpm install --frozen-lockfile`, `pnpm test`, and `pnpm build` all succeeded with the same 13 file / 114 test outcome.

On the sandbox side, the `interactive` profile (`src/profiles/interactive.ts`) and `build` profile (`src/profiles/build.ts`) allow `~/.npm` as a filesystem path (interactive: read + write; build: read only), and the `bootstrap` command's overlay fragment in `src/commands/bootstrap.ts` adds `~/.npm` to its write list. None of them include pnpm's macOS default store (`~/Library/pnpm`) or cache (`~/Library/Caches/pnpm`). The `inspect` profile does not include `~/.npm` and is out of scope for this migration's sandbox-policy change. The rendered `ios` profile currently inherits `INTERACTIVE_PROFILE` through `src/profiles/index.ts`, so interactive package-manager filesystem and network allowances (`~/.npm`, `registry.npmjs.org`, and the new pnpm paths) leak into iOS. This migration should fix that by making the iOS policy explicit rather than composing it from `INTERACTIVE_PROFILE`. `DEV_EGRESS_DOMAINS` in `src/profiles/dev-egress.ts` already includes `registry.npmjs.org`, which is the registry pnpm uses for `interactive` and build-with-egress workflows — no new network domain is required.

## Requirements

- The committed lockfile is `pnpm-lock.yaml`; `package-lock.json` is removed from the working tree.
- `package.json` includes a `packageManager` field set to `pnpm@11.1.1`. This field is treated as informational; Corepack adoption is not required of consumers.
- A `pnpm-workspace.yaml` at the repo root grants pnpm's build-script approval for `esbuild@0.21.5` so that `pnpm install --frozen-lockfile` does not fail with `ERR_PNPM_IGNORED_BUILDS`.
- The `smoke` script in `package.json` invokes pnpm (rather than npm) to build before running `scripts/smoke-test.sh`.
- The `justfile` invokes pnpm (rather than npm) for install and `pnpm exec` (rather than `npx`) for TypeScript compilation and Vitest invocations — covering the `build-ts` and `test` recipes.
- The README install section directs users to install pnpm by any reasonable mechanism (Homebrew, the npm global install, etc.) before running `pnpm install`. The smoke section uses `pnpm install`, `pnpm build`, `pnpm smoke`.
- The `interactive` profile's filesystem stance includes pnpm's macOS default store (`~/Library/pnpm`) and cache (`~/Library/Caches/pnpm`) paths in both its read and write allow lists, alongside the existing `~/.npm` allowance.
- The `build` profile's filesystem stance includes the same two pnpm paths in its read allow list (no write), alongside the existing `~/.npm` allowance.
- The bootstrap command's overlay fragment includes the same two pnpm paths in its write allow list, alongside the existing `~/.npm` allowance.
- The `inspect` profile is unchanged by this migration's sandbox-policy work.
- The rendered `ios` profile no longer composes `INTERACTIVE_PROFILE`. Its policy is an explicit allowlist that retains workspace and isolated Claude state access, temp writes, existing Xcode/Simulator/SwiftPM filesystem allowances, existing Apple/Swift package registry domains, and the GitHub Git-fetch domains needed for common Swift Package Manager dependencies. It must not inherit npm/pnpm/Yarn package-manager caches or npm/Yarn/PyPI/Cargo/Go/RubyGems/Maven/Docker registry domains from `interactive`.
- Profile tests cover the new pnpm allowances: the `interactive` test asserts the pnpm store/cache paths appear in both read and write allow lists after substitution; the `build` test asserts they appear in the read allow list and not in the write allow list. iOS profile tests assert rendered `ios` excludes `~/.npm`, `~/Library/pnpm`, `~/Library/Caches/pnpm`, `registry.npmjs.org`, and `registry.yarnpkg.com`, while retaining its expected iOS-specific allowances.
- Profile documentation for `interactive` and `build` lists the new pnpm paths in their filesystem-stance sections. Profile documentation for `ios` describes its explicit network and filesystem stance without claiming full `interactive` inheritance.

## Constraints

- `~/.npm` remains in `interactive`, `build`, and the bootstrap fragment — the sandbox-policy change is additive for those profiles, not subtractive. npm-using projects must continue to function inside the launcher's interactive/build sandboxes.
- `inspect` and rendered `ios` policies must not gain pnpm path allowances as part of this change; rendered `ios` also must not retain `~/.npm` via interactive inheritance.
- Do not solve the iOS leak by composing `INTERACTIVE_PROFILE` and filtering out package-manager entries afterward. The iOS policy should be explicit (factoring shared GitHub domains into a small constant is acceptable) so future interactive package-manager allowances cannot leak into iOS.
- The `packageManager` field stays informational; Corepack must not be a hard requirement of the install flow, and the README must not instruct users to run `corepack enable`.
- No new network domains are added. pnpm uses `registry.npmjs.org`, which is already in `INTERACTIVE_PROFILE` and `DEV_EGRESS_DOMAINS`. Corepack-from-inside-the-sandbox is not a supported workflow, so `nodejs.org` is not added to any domain set.
- The targeted pnpm version is `11.1.1`; the lockfile, the `packageManager` field, and any other version-bearing artifacts must agree on this version.
- All acceptance criteria from `docs/specs/2026-05-14-goal.md` must continue to hold — the smoke matrix's pass/deny outcomes, profile behavior, disposable-workspace guardrails, and isolated-state defaults must not regress.

## Acceptance Criteria

- `pnpm install --frozen-lockfile` succeeds from a clean checkout with no `ERR_PNPM_IGNORED_BUILDS` failures.
- `pnpm test` passes; the previously observed 13 files / 114 tests stand as a no-regression baseline (plus any tests added by this change).
- `pnpm build` produces `dist/cli.js`.
- `pnpm smoke` runs the full smoke-test matrix successfully (same pass/deny outcomes as the prior `npm run smoke`).
- `just test`, `just build-ts`, `just interactive`, `just build`, `just inspect`, `just ios`, `just bootstrap`, `just render`, and `just smoke` all execute their pnpm-equivalent commands without error.
- The repo contains `pnpm-lock.yaml` and `pnpm-workspace.yaml`, and no longer contains `package-lock.json`.
- `package.json` contains `"packageManager": "pnpm@11.1.1"`.
- No remaining `npm` or `npx` invocations in `package.json` scripts, `justfile` recipes, or the README's install and smoke sections. The README's `npm install -g @anthropic-ai/sandbox-runtime` line for installing SRT itself is independent of this migration and may remain.
- Profile tests assert pnpm cache/store paths in the expected allow lists for `interactive` and `build`.
- `docs/profiles/interactive.md` and `docs/profiles/build.md` list `~/Library/pnpm` and `~/Library/Caches/pnpm` in their filesystem-stance sections.
- Rendered `ios` profile output contains no npm/pnpm/Yarn filesystem paths or npm/Yarn package-registry domains, and tests lock this down while confirming expected iOS-specific paths/domains still render.

## Non-Goals

- Adding pnpm path allowances to the `inspect` or rendered `ios` profiles.
- Adding pnpm Linux store/cache paths (`~/.local/share/pnpm/store`, etc.) to any profile — macOS parity is sufficient for the current launcher scope; Linux support may follow when Linux SRT becomes a target.
- Requiring Corepack as the install path; it remains an option, not a mandate.
- Adding new network domains (e.g., `nodejs.org`) to any profile or dev-egress set.
- Removing `~/.npm` from `interactive`, `build`, or the bootstrap fragment.
- Bumping other dependency versions as part of this change.
- Migrating off Vitest or `tsc`; the build/test toolchain is unchanged apart from how it is invoked.
- Changing existing profile behavior outside the package-manager migration and explicit iOS package-manager leak cleanup.
